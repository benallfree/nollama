# Changelog

Every user-visible change gets a line under **Unreleased** in the commit that makes it. At a release, `## Unreleased`
becomes `## vX.Y.Z` and its lines are the release notes (`release/release.sh` reads them).

## Unreleased

## v0.0.1-alpha.3

- Integer models: new arithmetic (the distributions change; Surprisal 0.0.1-alpha.2's spec): activations into a matrix product have 12-bit mantissas, queries 12-bit, cached keys 16-bit and values 12-bit with one exponent per vector. Distributions are as sharp as before (Surprisal's archives within a byte) and the GPU runs faster: batched matrix products in exact float (their 64-term group sums are integers below 2^24), and one 32-bit multiply per attention score term. Metal batches (compression) run about 1.7x faster on an M1 Max with the 0.5B model. `NewWindowSession` runs a session with an attention window (the last N positions plus the first few), the same on the CPU, Metal and CUDA.
- Integer models: tokenizing a long run with no spaces or punctuation took quadratic time (a 16 KB run of letters 2.9 s, a megabyte hours); the merge is now O(n log n) (the 16 KB run: 7 ms). Same tokens.
- Integer models on Metal: a launch with more threads per group than its kernel can run is an error instead of silently wrong output; 7B-size models commit a command buffer every 6 launches, so macOS's GPU watchdog no longer kills long runs; a zero divisor in a kernel's division can't hang the GPU.

- x86 CPUs: the AVX2 kernels used a few legacy-SSE moves, which cost about 270 cycles each after AVX instructions on AMD EPYC Rome (Zen 2), about 60 on Intel Broadwell, and a little on Skylake. With every instruction VEX-encoded, output is the same bit for bit and writing speed (0.6B, Q4_K_M / Q8_0) goes from 2.3 / 0.7 to 24 / 19 tok/s on a 2 vCPU Rome server (Ollama 25 / 20), from 2.0 to 10.0 tok/s Q4_K_M on a 1 vCPU Broadwell server (Ollama 7.0), and Q8_0 writes about 50% faster on Skylake.
- Faster prompt reading on x86-64: Q4_K and Q6_K weights are multiplied two rows at a time against four prompt tokens on AVX2 (scales decoded once per tile), and four rows against sixteen tokens on AVX-512 (with VNNI when the CPU has it); F16 four rows against four tokens on AVX-512. Softmax, SwiGLU, rmsnorm and the activation quantizer are vectorized with AVX2. Every kernel keeps the reference order, so logits are bit for bit unchanged. On a 2 vCPU Cascade Lake server, Qwen3 1.7B Q4_K_M reads a 590-token prompt at 71 tok/s, up from 54 (Ollama 56 on the same server). `NOLLAMA_NO4X16=1` keeps the AVX2-shaped kernels and `AGENT_ENGINE_NOGEMM=1` the old 4-column ones.
- Packages moved (import paths change): `models` is now `catalog` (`github.com/benallfree/nollama/catalog`, package `catalog`), `schema` is now `engine/schema`, and the experimental `compose` and `audio` packages are now `x/compose` and `x/audio`. `engine`, `server` and `nollamatest` are unchanged. Developer tools moved to `tools/` (`go run ./tools/bench`, `go run ./tools/transcribe`).
- `bench report` prints one table per metric, nollama next to Ollama with the winner, from saved `bench vps` results, and with `-svg` draws the same comparisons as charts (a summary of every metric and one chart per metric), with absolute values as bars on a linear axis. The README and docs are rewritten: the guide is `docs/guide.md`, and `docs/benchmarks.md` holds only scripted results (raw data in `benchmarks/results`).
- Homebrew: nollama moved to the shared tap, `brew install benallfree/tap/nollama`. If you tapped `benallfree/nollama`, `brew update` moves you over.

## v0.0.1-alpha.2

- Integer models (`engine.LoadIntModel`, `engine.ConvertIntModel`, `nollama convert`): Qwen2.5 converted from the official weights into an integer-only forward pass whose next-token distributions are the same, bit for bit, on the CPU (NEON), Metal and CUDA, so an arithmetic coder built on them (like [Surprisal](https://github.com/benallfree/surprisal)) decodes exactly on any machine. Tokenizer access (`Tokenize`, `TokenBytes`, `ByteToken`), sessions (`NewSession`, `Feed`, batched `FeedBatch`) and pipelined decoding (`IntSession.Start`, `FindFeed`) on the GPU.
- Experimental speech recognition: `engine.LoadWhisper` opens OpenAI Whisper models in whisper.cpp's ggml format (`ggml-tiny.bin`, `ggml-base.bin`, ...; F16, F32 or Q8_0) and `Whisper.Transcribe` turns 16 kHz audio into text on the CPU, with language detection, translation to English, segment timestamps and 30 s windows for long audio. New `audio` package: a WAV reader with resampling and Whisper's log-mel spectrogram. `go run ./engine/cmd/transcribe -m ggml-base.bin clip.wav` tries it.
- Deterministic mode runs on the GPU on Macs: Metal kernels that give the CPU's logits bit for bit, about twice the CPU's writing speed and four times its prompt reading. NVIDIA GPUs (CUDA) get deterministic kernels too, with the same logits as the CPU and the Mac. The CPU's numbers change slightly (new golden hashes): rmsnorm now sums in float32 in a fixed order, and subnormals are flushed in rmsnorm, SwiGLU and the softmax, as GPUs do.
- CUDA: a kernel could run before a memory clear or copy issued just ahead of it had finished, and get its output overwritten (seen as zeros on an NVIDIA A16). Clears and copies now finish before the next kernel starts.
- Benchmarks on five Vultr cloud servers (1 to 4 vCPUs): time to first token from a cold and a warm start, with the model loaded, reading and writing speed and peak memory, next to Ollama on the same files (README, "On small cloud servers"). `go run ./engine/cmd/bench vps` measures the same on any Linux server, and `scripts/vultr-bench/vultr.sh` runs it on a fresh Vultr server and deletes the server afterwards.
- `nollama serve` can require an API key (`NOLLAMA_API_KEY` or `--api-key`; clients send `Authorization: Bearer <key>` or `X-API-Key`), and refuses to listen on a non-loopback address without one unless you pass `--insecure-public`.
- Requests from web pages not served from this machine, and requests whose `Host` is a domain other than `localhost` (DNS rebinding), are refused unless allowed with `--allowed-origins` / `--allowed-hosts` (or an API key is set, for hosts).
- The server no longer loads a model by a path outside its models folder (`"model": "/etc/passwd"`); `--allow-paths` turns that back on. A `.gguf` file in the models folder can be used by its name, and `hf:` downloads can't write outside the folder.
- `--read-only`, `--no-pull` and `--no-delete` turn off model management; `--models` limits which models clients may use.
- Request limits: body size (`--max-body-mb`, default 8), context window (`--max-num-ctx`, default 32768), answer length (`--max-tokens`), and requests open at once per client IP (`--per-client`, default 8).
- The same settings are fields of `server.Config` for embedders.
- `nollamatest` package: test code that uses nollama with no model download. A tiny random-weight Qwen3 model (about 1 MB, built in memory) runs the real engine; a scripted model answers with a function you write; `nollamatest.NewServer(t)` runs either behind the real Ollama/OpenAI HTTP server, answering to every catalog model name.
- `engine.LoadOptions.Respond` makes a model answer from a script instead of its weights, and `server.Config.Load` lets a test choose how model files are opened.
- Save and load a conversation's state, and the prompt cache's, through any `io.Writer`/`io.Reader` (`Model.SaveThread`, `LoadThread`, `SavePromptCache`, `LoadPromptCache`): a long conversation picks up after a restart without being read again. Snapshots are tied to the model file by a fingerprint, versioned and checksummed, half or full precision, optionally compressed.
- Embeddings: `/api/embed` (one text or a list, `truncate`, `dimensions`), `/api/embeddings` and `/v1/embeddings` (text or token ids, `dimensions`, `encoding_format` `float` or `base64`) answer with unit-length vectors from Qwen3-Embedding, which `qwen3-embedding-0.6b` (or `qwen3-embedding:0.6b`) downloads. In Go, `Model.Embed` and `engine.EmbedQuery` for the query instruction. `/api/show` reports an embedding model's capability as `embedding`.
- A prompt that doesn't fit the context window is an HTTP 400 that gives the token counts and the limit, in Ollama's and OpenAI's error shapes; nollama never truncates a prompt silently.
- Opt-in truncation: `"truncate": true` on `/api/chat` and `/v1/chat/completions`, or `nollama serve --truncate`, keeps the system prompt and the most recent messages, and reports what was dropped in a `truncated` field and the server log.
- `prompt_eval_count` and `eval_count` are always in Ollama's final answer, even when 0. `/v1/completions` streams `usage` with `stream_options.include_usage`.
- Engine: context errors are `*engine.ContextError` (matches `engine.ErrContextExceeded`) with the counts; `engine.TrimMessages` trims a conversation to a token budget.
- Models inside the binary: `nollama bundle -o <file> <model>...` adds GGUF files to the end of nollama or any Go program built with it, found by name and mmapped from the executable; `nollama bundle -check` verifies them. Go programs can also compile a model in with `go:embed` and `models.Embed`. A built-in model's path is `bundled:<name>` or `embedded:<name>`, which `engine.Load` opens, so loading by `src.Path` works for every model. New `engine.LoadRange`, `engine.LoadBytes`, `models.Bundle`, `models.Builtin`, `models.Available` and `models.Verify`; `/api/tags`, `/v1/models` and `nollama list` show built-in models.
- Tool calls: `tools` and `tool_choice` (`auto`, `none`, `required`, a named function) on `/v1/chat/completions` and `/api/chat`, streaming or not. Once the model starts a call, the rest of it is held to a listed tool and that tool's parameter schema, so calls always parse. `schema.CompileTools` and `engine.ChatPromptTools` do the same for Go programs.
- Resource budgets for apps that embed nollama: `engine.Resources` (or `server.Config` / `engine.LoadOptions`) shares one set of CPU threads across every model and answer, keeps weights, answers' state and caches inside a memory budget (freeing caches first, then failing with `engine.ErrMemoryLimit`, 503 from the server), and can run the engine's threads at a lower OS priority on Linux, macOS and Windows. `nollama serve` gets `--max-memory` and `--low-priority`, and `--threads` is now shared by all models; `NOLLAMA_THREADS`, `NOLLAMA_MAX_MEMORY` and `NOLLAMA_LOW_PRIORITY` set them too.
- Classify: `POST /api/classify` (nollama's own endpoint) and `Model.Classify` in Go take a prompt and candidate labels and return a probability for each, from one read of the prompt instead of generating and parsing an answer. Multi-token labels, `complete` (the label is the whole answer) and `normalize` (per-token scores); the prompt cache applies.
- Smaller KV cache: `nollama serve --kv-cache-type` (or `NOLLAMA_KV_CACHE_TYPE`, or `engine.LoadOptions.KVCacheType`) stores the attention cache as `f16`, `q8_0` or `q4_0` instead of `f32`, cutting its memory to 1/2, about 1/4 or about 1/5 for long contexts (`q4_0` keeps keys at 8 bits: 4-bit keys more than double Qwen3's perplexity). `/api/show` reports it as `nollama.kv_cache_type`.
- The same logits, bit for bit, on arm64 and amd64, with or without the assembly kernels, at any thread count and prompt batch size: every kernel (Go, NEON, AVX2; 1- and 4-token) sums in one reference order with single-rounding multiply-adds. A prompt read in batches (prefill, `Score`) no longer rounds differently from one read a token at a time. Logits change very slightly from before.
- Deterministic mode: `engine.LoadOptions.Deterministic` (`nollama serve --deterministic`, `NOLLAMA_DETERMINISTIC`, `nollama run --deterministic`) also makes logprobs portable (its own `exp`/`log`) and refuses compact KV caches and half-precision saved state.
- Speculative decoding (experimental: on the CPU engine today it makes answers slower, so it is off unless you ask for it): `nollama serve --draft qwen3-0.6b` (or `NOLLAMA_DRAFT`, `nollama run --draft`) loads a small model beside the one answering to guess a few tokens at a time, which the larger model checks in one pass. With temperature 0 the answer is exactly the one you'd get without it, and with sampling it follows the same distribution. `draft_tokens` in a request's options (0: off) and `--draft-tokens` set how many tokens it guesses. In Go: `engine.GenerateOptions.Draft` and `engine.CheckDraft`.

- Faster prompt reading on ARM64: Q4_K and F16 weights are multiplied two rows at a time against four prompt tokens (F16 as two pairs), Q6_K one row against four, with activations laid out so sub-block scales apply once per 64 weights. On an M1 Max the kernels run 1.37x (Q4_K), 1.16x (Q6_K) and 1.17x (F16) faster than the 4-column ones on one core. They follow the same reference order as every other kernel, so logits are bit for bit unchanged. `AGENT_ENGINE_NOGEMM=1` turns them off. x86-64 is unchanged.
- `nollama serve --keep-alive 0` (and `server.Config{UnloadWhenIdle: true}`) unloads the model as soon as its last answer finishes. Before, 0 quietly meant the 5-minute default.
- `NOLLAMA_KEEP_ALIVE` sets the server's keep-alive, in the same formats as Ollama's `OLLAMA_KEEP_ALIVE` (`300`, `5m`, `-1`).
- A request with `keep_alive: 0` that finishes while other answers are still being written now unloads the model once they finish, instead of being ignored.
- `/api/ps` always reports `expires_at` as a time (far in the future for a model kept loaded forever), never `""`, which Ollama's own client can't parse.
- README: "Loading and keep_alive" (what unloading saves and what it costs: the prompt cache), and the M1 Max next to the cloud servers, cold and warm first token and peak RAM.

## v0.0.1-alpha.1

First release.

- `nollama serve` answers Ollama's API (`/api/chat`, `/api/generate`, `/api/tags`, `/api/ps`, `/api/show`, `/api/pull`, `/api/delete`) and OpenAI's (`/v1/chat/completions`, `/v1/completions`, `/v1/models`), streaming or not, on `127.0.0.1:11434`.
- Structured output: Ollama's `format` (`"json"` or a JSON schema) and OpenAI's `response_format` (`json_object`, `json_schema`) limit the answer to JSON that matches, token by token.
- `nollama run`, `pull`, `list` and `rm` in the terminal.
- Qwen3 models (0.6B, 1.7B, 4B by name; any Qwen3 GGUF from Hugging Face or a file) in Q8_0, Q4_K_M, F16 or BF16, on the CPU, with assembly kernels for ARM64 (NEON, dot product) and x86-64 (AVX2, FMA).
- Go packages to embed it: `server` (the HTTP handler), `engine` (load a model and generate), `models` (find and download models), `schema` (JSON schema constraints).
- Installs with Homebrew, Scoop, `install.sh`, or `.deb`/`.rpm`/`.apk` packages that add a systemd service.
